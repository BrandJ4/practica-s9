## Solución propuesta

### 1. Framework de priorización MoSCoW
Clasificar cada tarea en el backlog:
- **Must Have:** Sin esto, el sistema no funciona o el cliente no acepta la entrega
- **Should Have:** Importante, pero el sistema funciona sin ello
- **Could Have:** Deseable si hay tiempo disponible
- **Won't Have:** Descartado para este sprint/versión

### 2. Labels en GitHub Issues
```
priority: must-have   (rojo)
priority: should-have (naranja)  
priority: could-have  (amarillo)
priority: wont-have   (gris)
```

### 3. Backlog refinement semanal
30 minutos semanales para:
- Revisar y repriorizar el backlog
- Asegurarse de que los Must Have del próximo sprint están bien definidos
- Descartar o diferir tareas Could Have si el backlog está lleno

### 4. Regla 80/20 en el sprint
- 80% del tiempo del sprint: tareas Must Have y Should Have
- 20% máximo: tareas Could Have y mejoras técnicas

### 5. Validar prioridades con el cliente
En la Sprint Review, mostrar primero las funcionalidades Must Have y obtener validación explícita del cliente.
